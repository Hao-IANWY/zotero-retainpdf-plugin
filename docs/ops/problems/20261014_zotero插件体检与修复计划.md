# 20261014 Zotero 插件体检与修复计划

## 背景

老板对 zotero-retainpdf-plugin 做体验体检，报告三个问题：

1. 监控台入口出现在条目右键菜单（不想要），想要的工具栏入口不存在，且监控台打不开；监控台地址不应让用户填，就是后端地址。
2. 偏好页 LLM Key 输入框有两个"眼睛"图标（注入的 + Gecko 原生），要求全部去掉、直接明文。
3. 偏好页模型下拉不可用（只剩残留值，刷新拉不到列表）。

体检过程中另发现两个无症状隐患，一并列入。

## 问题清单与根因诊断

### P1 监控台：入口错位 + 打不开 + 地址多余

**入口现状**（`plugin/src/modules/monitorWindow.ts` `registerMonitorMenuItems`）：
注册了「工具菜单」+「条目右键菜单」双入口，无工具栏按钮。

**地址现状**：`monitorRootURL()` 优先读 `monitorUrl` pref，留空回退 `serverBaseURL`；
偏好页有独立「监控台地址（可选）」输入框。老板拍板：地址就是服务地址，不单独配。

**打不开的根因**（按嫌疑排序）：

a. **XUL `<browser>` 缺 `type="content"`（主嫌疑，静态分析可定性）**。
   ztoolkit Dialog 经 `openDialog("about:blank", …)` 从 chrome 上下文开窗，窗口文档是
   chrome 文档；XUL `<browser>` 不显式声明 type 时默认以 chrome 权限加载内容，Gecko
   安全策略禁止远程 URL 以 chrome 权限加载——`src` 被静默拒绝，窗口打开后白屏。
   当前 `buildWindow` 只设了 `flex` 和 `src`，未设 `type="content"`。

b. **服务地址指向 Cloudflare Access 公网域名（环境嫌疑）**。
   开窗前探测 `GET {root}/index.html`，CF Access 在边缘拦截返回非 200，插件弹
   「监控台不可达」右下角通知（8 秒自动关闭），观感等同"打不开"。
   v1 设计本就只支持无边缘认证直连（本机/内网/tailscale），
   默认 `serverBaseURL=http://127.0.0.1:40001` 即 web 容器（nginx 同原点静态页 + API 反代）。

**修复方案**：

- 删除条目右键菜单入口（`item`），保留工具菜单入口作兜底；
  新增主窗口工具栏按钮：向 `#zotero-toolbar` 注入 `toolbarbutton`，
  点击即 `openMonitorWindow()`；窗口卸载时移除按钮。
- 删除 `monitorUrl` pref、偏好页输入框与对应 ftl 文案；
  `monitorRootURL()` 直读 `serverBaseURL`。
- `<browser>` 补 `type="content"` + `disablehistory="true"`。
- 不可达通知文案更新：去掉「单独填写监控台地址」指引，改为确认服务地址指向
  web 入口（40001）而非后端 API 端口或 CF Access 公网域名。

### P2 密钥框双眼睛 → 全明文化

**根因**：Gecko 112+ 给每个 `type=password` 输入框内渲染原生显隐眼睛，
插件又注入了一个外围眼睛按钮，叠成两只。v0.1.7 曾尝试启动期关
`layout.forms.reveal-password-button.enabled` pref，老板实测截图仍双眼，方案无效。

**老板拍板**：密钥框全部明文，眼睛连根拔。

**修复方案**：

- `preferences.xhtml` 三个密钥框（paddleToken / mineruToken / llmApiKey）
  `type="password"` → `type="text"`。
- 删 `preferenceScript.ts` 的眼睛注入代码块与 `EYE_OPEN_SVG`/`EYE_OFF_SVG` 常量。
- 删 `hooks.ts` 启动期关 Gecko pref 的代码块（没有密码框了，不再需要）。
- 删 ftl 的 `pref-show-key` / `pref-hide-key`。
- CSS 的 `.rp-icon-btn` 保留（模型刷新按钮共用），无其他清理。

### P3 模型下拉不可用

**症状**：下拉只有残留值 `deepseek-flash`（DeepSeek 官方仅 deepseek-chat /
deepseek-reasoner，此值疑似历史自定义端点分槽残留），刷新拉不到新列表。

**已排除**：端点本身存活（裸请求 `GET https://api.deepseek.com/v1/models`
返回 401 待鉴权，OpenAI 兼容格式）；preference 绑定前缀化在构建产物中验证无误。

**候选根因（待实测确认）**：

a. 拉取确实失败（网络代理 / key 失效），状态行已有错误文案（v0.1.7 加的）
   但未被注意——`Zotero.HTTP.request` 走 Zotero 自身代理设置，系统代理不生效时会超时。
b. 下拉初始只填残留值，用户不点刷新永远只有一个无效选项——交互引导不足。

**修复方案**：

- 偏好页打开时若 baseUrl + key 齐备，自动触发一次 `fetchModels`
  （现在必须手动点刷新或检查连接，老板没感知到这个按钮）。
- 实测复现一次刷新动作，读取状态行错误文案定根因；
  若为代理问题，在文档/README 写清 Zotero 代理要求。
- 下拉刷新成功后已保存值不在列表时的回落逻辑已有（`fillModelOptions`），不动。

### P4（体检附加发现）prefs.js 默认值从未被加载

**根因**：`addon/bootstrap.js` 的 `startup()` 没有加载 `prefs.js` 的逻辑，
Zotero 7 也不会自动加载插件的 prefs.js；scaffold 只在构建期把它前缀化并复制进产物。
全仓 grep 确认运行时无任何 `loadSubScript("prefs.js")` 等价物。

**后果**：新用户首次安装时所有默认值为空——`serverBaseURL` 默认
`http://127.0.0.1:40001` 不生效；`new RetainPdfClient()` 在 pref 缺失时
`undefined.replace()` 抛 TypeError（被各检查函数 catch，但提示语怪异）。
老用户因手动填过值无感知。

**修复方案**：bootstrap.js 补 zotero-plugin-template 标准 `setDefaultPrefs` 片段
（`Services.prefs.getDefaultBranch("")` + `loadSubScript(rootURI + "prefs.js")`），
startup 早期调用。

### P5（体检附加发现）prefs.js 键名风格不一致

`monitorUrl` / `monitorWindow` 写了全前缀，其余键无前缀。构建期
`getPrefsWithPrefix` 对已带前缀的键原样保留，碰巧结果正确，但风格不统一易误导。
P1 删除 `monitorUrl` 后，顺手把 `monitorWindow` 归一为无前缀。

## 第二轮：v0.1.8 真机实测反馈与根因（2026-10-14 当日）

老板装机实测后反馈三问题，根因与对策如下：

### R1 工具栏按钮根本没出现（「不要放工具栏，要放我指的地方」）

**根因**：Zotero 7 主窗口**不存在 `#zotero-toolbar`**（直接拉 zotero/zotero 源码
`zoteroPane.xhtml` 确认）。条目区工具栏的真实结构：

```
<toolbar id="zotero-toolbar-item-tree">
  <hbox id="zotero-items-toolbar">
    …左侧工具按钮(zotero-tb-add 等)…
    <spacer flex="1"/>
    <image id="zotero-tb-search-spinner"/>
    <quick-search-textbox id="zotero-tb-search"/>   ← 搜索框
    <toolbarbutton id="zotero-tb-toggle-item-pane-stacked"/>
  </hbox>
</toolbar>
```

v0.1.8 注入 `getElementById("zotero-toolbar")` 拿到 null，静默跳过——按钮从未出现。
老板截图箭头所指（搜索栏右侧、过滤按钮旁）就是 `#zotero-items-toolbar` 末尾
（spacer 把搜索区顶到右边，老板说的"工具栏"和他指的位置在 DOM 里是同一容器
的两段）。

**修复**：注入点改 `#zotero-items-toolbar` 末尾（逐层回退：
`zotero-tb-search` 父元素 → `zotero-toolbar-item-tree`）；图标改
`image` 属性 + `list-style-image` 双保险（Zotero 7 对两种图标机制的覆盖随版本变）。

### R2 监控台仍打不开

老板服务侧探活全部正常（curl 经 tailscale：web 40001 /health 200、
/index.html 200、LLM 网关 8084 /v1/models 401 待鉴权）。问题在 Zotero 侧，
候选：探测请求被 Zotero 代理设置劫持（见 R3）、开窗/browser 加载异常。

**对策（可观测性先行）**：开窗全链路写插件日志（profile/retainpdf-plugin.log）——
入口 root 值、探测结果、buildWindow 异常、browser 的 load/error 事件；
探测失败时若地址是内网 IP 且 `network.proxy.type != 0`，日志直接点名代理配置。
老板复现后发日志文件即可定位卡在哪一步。

### R3 LLM 检查「验证失败：network error」

**链路澄清**：LLM「检查连接」走的是**后端探针**
（POST `{serverBaseURL}/api/v1/providers/deepseek/validate-token`，由后端去连
LLM 网关），network error = **Zotero 连不上 serverBaseURL**，与 8084 网关本身无关
（网关 curl 实测 401 正常存活）。

**根因候选**：a. Zotero 代理设置把 tailscale 内网地址发给代理（本机 curl 不走
代理所以通）；b. serverBaseURL 值不对（如残留 127.0.0.1 而 Zotero 不在部署机上）。

**修复**：api.ts 网络错误兜底从笼统 "network error" 改为带出底层细节
（`network error (status=0 …)`），检查失败同步落插件日志；监控台不可达通知
文案补代理提示。v0.1.9 装机后状态行/日志会直接显示真实原因。
